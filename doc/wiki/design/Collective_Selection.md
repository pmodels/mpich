# Collective Algorithm Selection (CSEL)

This page describes how MPICH selects the algorithm for a collective call.
Selection happens in one step at the MPIR layer. All algorithms, including
device-specific ones, are listed in one catalog, `coll_algorithms.txt`. A JSON
decision tree, `coll_selection.json`, picks among them. Most of the glue code
is generated by `maint/gen_coll.py` from the catalog.

## Background

The previous design selected in two levels: `MPIR_Xxx` picked an MPIR
algorithm or "call the device", and `MPID_Xxx` (CH4) ran its own JSON trees for
composition, netmod, and POSIX shm. The csel core treated algorithm leaves as
opaque containers parsed by hand-written code (`csel_container.c`), pruned a
copy of the tree per communicator, and each collective's `_impl` repeated its
own CVAR, restriction, and fallback logic. The redesign (PRs #8006, #8009,
#8010, #8013, #8016, #8017, #8018, #7547; RFC in discussion #7544) replaced all
of this.

## Concepts

Every collective call becomes one value, the *collective signature*
(`coll_sig`). Every algorithm is one function type that takes a `coll_sig` and
a *container*. Selection walks a tree of conditions over the `coll_sig` until
it reaches a container, then calls that container's function.

| Concept | C type / symbol | What it is |
|---|---|---|
| Collective type | `MPIR_Csel_coll_type_e`, e.g. `MPIR_CSEL_COLL_TYPE__INTRA_BCAST` | One value per collective × intra/inter × blocking/nonblocking. Blocking values are even; the nonblocking form is +1. Generated. |
| Collective signature | `MPIR_Csel_coll_sig_s` (`src/include/mpir_coll.h`) | `coll_type`, `comm_ptr`, `tag`, `sched`, `sched_type`, `flags`, and a union of the call's arguments (`u.bcast.buffer`, ...). Passed by pointer, so it carries state through nested selections. |
| Algorithm ID | `MPII_Csel_container_type_e` | One ID per algorithm in the catalog, with a name table `MPIR_Coll_algo_names`. Generated. |
| Container | `MPII_Csel_container_s` | The selected algorithm: its `id` and a union of per-algorithm extra parameters (tree kval, chunk size, ...). |
| Algorithm function | `MPIR_Coll_algo_fn`: `int (*)(coll_sig, cnt)` | Uniform entry point. A generated `<algo>_cnt` wrapper per algorithm unpacks the `coll_sig` and calls the real function. All wrappers are in `MPIR_Coll_algo_table[id]`. |
| Condition | `bool f(coll_sig)`, or `int f(coll_sig)` with a threshold | Named predicates such as `pof2`, `inplace`, `comm_size(thresh)`. Used both as JSON branch keys and as algorithm restrictions. |
| Tree node | `MPIR_Csel_node_s` (`src/mpi/coll/include/coll_csel.h`) | A `type` (collective, any, a condition, call, or container), `negate` and `thresh` for conditions, and `success`/`failure` pointers. |
| General algorithm | `MPIR_Coll_nb` | An algorithm that works for any `coll_type`; selectable like any other. |

Three inputs drive selection:

1. `src/mpi/coll/coll_algorithms.txt`, the catalog of conditions and
   algorithms.
2. `src/mpi/coll/coll_selection.json`, the default decision tree. It is
   compiled into the library and can be extended or overridden at run time
   with `MPIR_CVAR_COLL_SELECTION_JSON_FILE`.
3. The per-collective algorithm CVARs, e.g. `MPIR_CVAR_BCAST_INTRA_ALGORITHM`,
   which force one algorithm and are checked before the tree.

## The catalog: `coll_algorithms.txt`

The file is indentation based (4 spaces; the `:` after a key is significant).
It has three kinds of top-level section:

```
conditions:
    inplace:                MPIR_Csel_sendbuf_inplace
    pof2:                   MPIR_Csel_comm_size_is_pof2
    comm_size(thresh):      MPIR_Csel_comm_size
    avg_msg_size(thresh):   MPIR_Csel_avg_msg_size
    MPIDI_CH4_release_gather: MPIDI_POSIX_check_release_gather #if defined(MPIDI_CH4_SHM_POSIX)

general:
    MPIR_Coll_nb

bcast-intra:
    binomial
    smp
        restrictions: hierarchical
    tree
        extra_params: tree_type, k, is_non_blocking
        cvar_params: TREE_TYPE, TREE_KVAL, IS_NON_BLOCKING
    release_gather
        func_name: MPIDI_POSIX_mpi_bcast_release_gather
        inline: 1
        macro_guard: defined(MPIDI_CH4_SHM_POSIX)
        restrictions: MPIDI_CH4_release_gather
```

- **Conditions.** `name: func` is a predicate, `bool func(coll_sig)`.
  `name(thresh): func` is a query, `int func(coll_sig)`, and the condition is
  true when the value is at most the threshold. A trailing `#if ...` makes a
  *conditional condition*: the generated wrapper calls `func` only under that
  macro guard and returns false otherwise.
- **General algorithms** work on any `coll_type`. `MPIR_Coll_nb` runs the
  nonblocking form of a blocking collective and waits for it.
- **`<coll>-<intra|inter>` sections** list algorithms. A name such as
  `binomial` expands to the function `MPIR_Bcast_intra_binomial` unless
  `func_name` gives one. Attribute keys:
    - `restrictions`: conditions that must hold for the algorithm to run.
      Prefix with `!` to negate. Threshold conditions are not allowed here.
    - `extra_params` and `cvar_params`: extra arguments of the algorithm
      function, and the CVAR suffixes that supply them when the algorithm is
      forced by CVAR. The CVAR's type is also the parameter's type in the
      JSON (see below). `name=value` fixes a constant, with `-` as its
      `cvar_params` placeholder.
    - `func_name`, `inline`, `macro_guard`: for device algorithms that are
      inline in device headers and exist only in some builds.

Each entry is exactly one algorithm function. There are no aliases; an alias
is a small separate function.

## The decision tree: `coll_selection.json`

Each JSON object is a list of sibling branches, tried in order. A key is a
test and its value is the subtree taken when the test passes. When a test
fails, the next sibling is tried. A leaf is an `algorithm=` key.

| Key form | Meaning |
|---|---|
| `name=bcast-intra-auto` | Top level only: defines a named subtree. |
| `collective=bcast-intra` | Matches the `coll_type` (names from `MPIR_Coll_type_names`). |
| `pof2`, `!pof2` | Boolean condition, optionally negated. |
| `comm_size(8)` | Canonical threshold form: `comm_size <= 8`. |
| `comm_size<8`, `<=`, `>`, `>=` | Aliases: `cond<t` is `cond(t-1)`, `cond>t` is `!cond(t)`, `cond>=t` is `!cond(t-1)`. A leading `!` is an error with these; write `!comm_size(8)` or flip the comparison. |
| `any` | Always true. Used as the last sibling. |
| `algorithm=MPIR_Barrier_intra_k_dissemination` | Leaf. Its object holds the algorithm's extra parameters, e.g. `{"k": 2}`; see below. |
| `"call=bcast-intra-auto"` | A string value in place of an object: continue the search in that named subtree. |

The file is a dictionary of named subtrees:

```json
{
    "name=main": "call=auto",
    "name=auto": {
        "collective=bcast-intra": "call=bcast-intra-auto",
        "collective=allreduce-intra": "call=allreduce-intra-auto",
        ...
    },
    "name=bcast-intra-auto": {
        "MPIDI_CH4_release_gather": { "algorithm=MPIDI_POSIX_mpi_bcast_release_gather": {} },
        "comm_size<8":              { "algorithm=MPIR_Bcast_intra_binomial": {} },
        "pof2": {
            "avg_msg_size<=12288":  { "algorithm=MPIR_Bcast_intra_binomial": {} },
            "avg_msg_size<=524288": { "algorithm=MPIR_Bcast_intra_scatter_recursive_doubling_allgather": {} },
            "any":                  { "algorithm=MPIR_Bcast_intra_scatter_ring_allgather": {} }
        },
        "any": { ... }
    },
    ...
}
```

- `main` is where every user-level collective starts. `auto` is what nested
  selections search (see below). If a file defines no `auto`, `main` is used.
- The built-in JSON is loaded first. A file named by
  `MPIR_CVAR_COLL_SELECTION_JSON_FILE` is loaded on top of it: each `name=` it
  defines replaces the built-in subtree of that name, and new names are added.
  To retune one collective, a user file only needs that one subtree, e.g.
  `name=bcast-intra-auto`.
- A file with no `name=` keys is loaded as a single tree named `main`.
- `call=` targets are resolved by name at search time, so a subtree replaced
  by the user file is the one used.

An algorithm leaf lists every non-constant parameter in its `extra_params`
as `"name": value`, and nothing else. The value's type follows the type of the
parameter's CVAR in `cvar_params`:

| CVAR type | JSON value | Example |
|---|---|---|
| `int` | an integer | `"k": 4`, `"chunk_size": 8192` |
| `boolean` | `true` or `false` | `"is_non_blocking": true` |
| `enum` | one of the CVAR's value names, as a string | `"tree_type": "knomial_1"`, `"ccl": "nccl"` |

```json
"algorithm=MPIR_Bcast_intra_tree": { "tree_type": "kary", "k": 4, "is_non_blocking": false }
```

A missing, unknown, or mistyped parameter is an error.

The tree does not check algorithm restrictions. A tree must pick only
algorithms whose restrictions hold on that branch, for example by guarding
`MPIR_Allreduce_intra_reduce_scatter_allgather` with `builtin_op` and
`count_ge_pof2`.

The files are read by a small built-in parser (`csel_json.c`) that accepts
only the JSON subset the tree needs:

- The top level is an object, and every value is an object, a string, an
  integer (fits in an `int`), `true`, or `false`. Floats, arrays, and `null`
  are rejected.
- Strings are printable ASCII without escape sequences. Spaces inside a string
  are dropped, so `"comm_size < 8"` is read as `comm_size<8`.
- Keys within an object must be unique. Objects nest at most 64 levels.
- A syntax error, an unknown subtree, collective, algorithm, or condition, a
  malformed threshold, or a bad algorithm parameter stops `MPI_Init` with the
  line and column of the error.

## Runtime selection

```
MPI_Bcast
  -> MPIR_Bcast_impl                 (generated) fill coll_sig, MPID_Init_coll_sig
     -> MPIR_Coll_json
        algorithm CVAR set?
          yes: restrictions pass? -> fill container from CVARs ------+
               no: error if MPIR_CVAR_COLLECTIVE_FALLBACK=error,      |
                   otherwise fall through                             |
        MPIR_Coll_run_tree(main)                                      |
          -> MPIR_Csel_search -> container ---------------------------+
                                                                      v
                                          MPIR_Coll_algo_table[id](coll_sig, cnt)
                                            -> <algo>_cnt wrapper -> algorithm
  <- nonblocking: MPII_SCHED_START; persistent: save sched in the request
```

1. **Binding.** `MPI_Bcast` calls `MPIR_Bcast_impl`, as for every other MPI
   function. The `_impl` functions are generated.
2. **Signature.** `_impl` fills a stack `coll_sig`: `coll_type`, `comm_ptr`,
   `flags` (`MPIR_COLL_SIG_FLAG__PERSISTENT` for `_init` calls), `tag`,
   `sched = NULL`, and the arguments. It then calls
   `MPID_Init_coll_sig(&coll_sig)` so the device can add its own fields.
3. **CVAR.** `MPIR_Coll_json` reads `MPIR_Coll_cvar_table[coll_type]`; 0 means
   `auto`. Otherwise it sets `MPIR_COLL_SIG_FLAG__CVAR`, maps the value to an
   algorithm ID (`MPIR_Coll_cvar_to_algo_id`), and checks
   `MPIR_Coll_check_algo_restriction`. If the check passes, it fills a
   container from the CVAR parameters (`MPIR_Coll_init_algo_container`) and
   runs the algorithm. If it fails, it returns an error when
   `MPIR_CVAR_COLLECTIVE_FALLBACK=error` and falls through to the tree
   otherwise.
4. **Search.** `MPIR_Csel_search` walks the tree from `main`. A `collective`
   node compares `coll_type`. A condition node calls the generated
   `MPII_Csel_run_condition`, which evaluates the predicate (or `<= thresh`),
   then applies `negate`. `any` always passes. A match moves to `success`, a
   miss to `failure` (the next sibling). A `call` node continues in the named
   subtree. The search ends at a container.
5. **Run.** `MPIR_Coll_algo_table[cnt->id](coll_sig, cnt)` calls the `_cnt`
   wrapper. It increments `MPIR_Coll_algo_counters[id]`, creates the schedule
   for a nonblocking algorithm (`MPII_CSEL_CREATE_SCHED` or
   `MPII_CSEL_CREATE_TSP_SCHED`), and calls the algorithm with the unpacked
   arguments and extra parameters. Back in `_impl`, a nonblocking call starts
   the schedule and a persistent call stores it in a new persistent request.

Rules that follow:

- **Algorithms do not fall back on their own.** An algorithm whose
  restrictions fail is an error. Restrictions are checked once, before a
  CVAR-forced algorithm runs; the tree is responsible for the auto path.
- **Blocking via nonblocking.** `MPIR_Coll_nb` adds 1 to `coll_type`, runs
  selection on the `auto` tree, then starts and waits on the resulting
  schedule. It is chosen by the algorithm CVAR value `nb` or by
  `algorithm=MPIR_Coll_nb` in the JSON.
- **Nested selection.** Because `coll_sig` is passed by pointer and carries
  `sched`, `tag` and `flags`, an algorithm can re-enter selection for a
  sub-step with `MPIR_Coll_run_tree(csel_tree_auto, coll_sig)`. The outer
  entry (`main`) and the inner sub-steps (`auto`) can be tuned separately.
- **One global tree.** There is no per-communicator pruning or caching; every
  call searches from the root.
- **Usage counters.** `MPIR_CVAR_DUMP_COLL_ALGO_COUNTERS=<world rank>` makes
  that rank print a count per algorithm at finalize. Internal `_fallback`
  collectives (used during init and communicator creation) bypass CSEL and are
  not counted.

```
[0] ==== Dump collective algorithm counters ====
[0]          4  MPIR_Bcast_intra_scatter_ring_allgather
[0]         16  MPIDI_POSIX_mpi_bcast_release_gather
[0]          1  MPIR_Reduce_intra_binomial
[0] ==== END collective algorithm counters ====
```

## Generated code

`maint/gen_coll.py` reads the catalog and generates:

| Output | Generated items |
|---|---|
| Types | `MPIR_Csel_coll_type_e`, `MPII_Csel_container_type_e`, `MPIR_Csel_node_type_e`, `MPII_Csel_container_s` |
| Tables | `MPII_Coll_type_init` (`MPIR_Coll_type_names`, `MPIR_Coll_cvar_table`), `MPII_Coll_algo_init` (`MPIR_Coll_algo_table`, `MPIR_Coll_algo_names`), `MPII_Csel_init_condition_names` (`MPIR_Csel_condition_names`, `MPIR_Csel_condition_has_thresh`) |
| JSON parsing | `MPII_Csel_parse_container_params` |
| Search | `MPII_Csel_run_condition` |
| CVAR path | `MPIR_Coll_cvar_to_algo_id`, `MPIR_Coll_init_algo_container`, `MPIR_Coll_check_algo_restriction` |
| Dispatch | the `<algo>_cnt` wrappers and every `MPIR_Xxx_impl` |

`coll_algos.h` is included from `mpir_coll.h`, between `mpidpre.h` and
`mpidpost.h`. Code that calls device functions (conditional-condition
wrappers) goes into `coll_autogen.h`, which is included after `mpidpost.h`.

## Device algorithms

There is no MPID collective ADI. A device takes part in selection by exposing
algorithms that are listed in the catalog, supplying conditions, and adding
fields to `coll_sig`. CH4 POSIX `release_gather` (bcast, reduce, allreduce,
barrier) is the example.

- **Algorithm.** `src/mpid/ch4/shm/posix/posix_coll.h` exposes inline
  functions such as `MPIDI_POSIX_mpi_bcast_release_gather`. The catalog lists
  them with `func_name`, `inline: 1`, and
  `macro_guard: defined(MPIDI_CH4_SHM_POSIX)`; in other builds the generated
  wrapper returns `MPI_ERR_OTHER`. The algorithm CVAR gains the value
  `release_gather`, and the JSON names the function like any MPIR algorithm.
- **Condition.** `MPIDI_CH4_release_gather` is a conditional condition, so the
  same tree works for CH3 and every CH4 configuration.
  `MPIDI_POSIX_check_release_gather` rejects threaded runs, communicators that
  span nodes (`num_external > 1`), and unsupported reduce types or
  non-commutative ops. It passes only after
  `MPIR_CVAR_POSIX_NUM_COLLS_THRESHOLD` calls on the communicator, except when
  `MPIR_COLL_SIG_FLAG__CVAR` is set. It lazily initializes the shared-memory
  state and passes only if that succeeds. Every communicator, including
  `node_comm` and `node_roots_comm`, carries `MPIR_COMM_ATTR__HIERARCHY`, so
  such checks can rely on the hierarchy fields.
- **Signature hook.** Every `_impl` calls `MPID_Init_coll_sig(coll_sig)` after
  the generic fields are set. CH3 and CH4 define it as an empty inline today.
  New boolean attributes go in the `flags` bit mask.

## Adding an algorithm

1. Write the algorithm function with the standard collective arguments, plus
   any extra parameters.
2. List it under its `<coll>-<intra|inter>` section in `coll_algorithms.txt`
   with its `restrictions`, `extra_params`, and `cvar_params`. Add any new
   condition under `conditions:` and define its checker function.
3. Add its value to the collective's algorithm CVAR in
   `src/mpi/coll/cvars.txt`.
4. Reference it in `coll_selection.json` on branches where its restrictions
   hold.
