# Collective Algorithm Selection (CSEL)

This page describes how MPICH selects the algorithm for a collective call.
Selection happens in one step at the MPIR layer. All algorithms, including
device-specific ones, are listed in one catalog, `coll_algorithms.txt`. A JSON
decision tree, `coll_selection.json`, picks among them. Most of the glue code
is generated by `maint/gen_coll.py` from the catalog.

## Background

The previous design selected in two levels: `MPIR_Xxx` picked an MPIR
algorithm or "call the device", and `MPID_Xxx` (CH4) ran its own JSON trees for
composition, netmod, and POSIX shm. The csel core treated algorithm leaves as
opaque containers parsed by hand-written code (`csel_container.c`), pruned a
copy of the tree per communicator, and each collective's `_impl` repeated its
own CVAR, restriction, and fallback logic. The redesign (PRs #8006, #8009,
#8010, #8013, #8016, #8017, #8018, #7547; RFC in discussion #7544) replaced all
of this.

## Concepts

Every collective call becomes one value, the *collective signature*
(`coll_sig`). Every algorithm is one function type that takes a `coll_sig` and
a *container*. Selection walks a tree of conditions over the `coll_sig` until
it reaches a container, then calls that container's function.

| Concept | C type / symbol | What it is |
|---|---|---|
| Collective type | `MPIR_Csel_coll_type_e`, e.g. `MPIR_CSEL_COLL_TYPE__INTRA_BCAST` | One value per collective × intra/inter × blocking/nonblocking. Blocking values are even; the nonblocking form is +1. Generated. |
| Collective signature | `MPIR_Csel_coll_sig_s` (`src/include/mpir_coll.h`) | `coll_type`, `comm_ptr`, `tag`, `sched`, `sched_type`, `flags`, and a union of the call's arguments (`u.bcast.buffer`, ...). Passed by pointer, so it carries state through nested selections. |
| Algorithm ID | `MPII_Csel_container_type_e` | One ID per algorithm in the catalog, with a name table `MPIR_Coll_algo_names`. Generated. |
| Container | `MPII_Csel_container_s` | The selected algorithm: its `id` and a union of per-algorithm extra parameters (tree kval, chunk size, ...). |
| Algorithm function | `MPIR_Coll_algo_fn`: `int (*)(coll_sig, cnt)` | Uniform entry point. A generated `<algo>_cnt` wrapper per algorithm unpacks the `coll_sig` and calls the real function. All wrappers are in `MPIR_Coll_algo_table[id]`. |
| Condition | `bool f(coll_sig)`, or `int f(coll_sig)` with a threshold | Named predicates such as `pof2`, `inplace`, `comm_size(thresh)`. Used both as JSON branch keys and as algorithm restrictions. |
| Tree node | `MPIR_Csel_node_s` (`src/mpi/coll/include/coll_csel.h`) | A `type` (collective, any, a condition, call, or container), `negate` and `thresh` for conditions, and `success`/`failure` pointers. |
| General algorithm | `MPIR_Coll_nb` | An algorithm that works for any `coll_type`; selectable like any other. |

Three inputs drive selection:

1. `src/mpi/coll/coll_algorithms.txt`, the catalog of conditions and
   algorithms.
2. `src/mpi/coll/coll_selection.json`, the default decision tree. It is
   compiled into the library and can be extended or overridden at run time
   with `MPIR_CVAR_COLL_SELECTION_JSON_FILE`.
3. The per-collective algorithm CVARs, e.g. `MPIR_CVAR_BCAST_INTRA_ALGORITHM`,
   which force one algorithm and are checked before the tree.

## The catalog: `coll_algorithms.txt`

The file is indentation based (4 spaces; the `:` after a key is significant).
It has four kinds of top-level section:

```
restrictions:
    0  - inplace:           MPIR_Csel_sendbuf_inplace
    1  - pof2:              MPIR_Csel_comm_size_is_pof2

conditions:
    comm_size(thresh):      MPIR_Csel_comm_size
    msg_size(thresh):       MPIR_Csel_msg_size
    MPIDI_CH4_release_gather: MPIDI_POSIX_check_release_gather #if defined(MPIDI_CH4_SHM_POSIX)

general:
    MPIR_Coll_nb

bcast-intra:
    binomial
    smp
        restrictions: hierarchical
    tree
        extra_params: tree_type, k, is_non_blocking
        cvar_params: TREE_TYPE, TREE_KVAL, IS_NON_BLOCKING
    release_gather
        func_name: MPIDI_POSIX_mpi_bcast_release_gather
        inline: 1
        macro_guard: defined(MPIDI_CH4_SHM_POSIX)
        restrictions: MPIDI_CH4_release_gather
```

- **Restrictions and conditions** form one condition table, restrictions
  first. `index - name: func` under `restrictions:` is a predicate,
  `bool func(coll_sig)`, usable both as an algorithm restriction and in JSON.
  The index is its position in the table (gen_coll checks it) and its bit in
  the masks tuning tools use, e.g. in tuning-file subtree names, so existing
  indices must not change and new restrictions go at the end.
  `name(thresh): func` under `conditions:` is a query, `int func(coll_sig)`,
  and the condition is true when the value is at most the threshold; it is
  for JSON only. `msg_size` is the message size in bytes, the same on every
  rank of the call: the buffer of bcast, reduce, allreduce, scan and exscan,
  one rank's block of allgather, alltoall, gather, scatter and
  reduce_scatter_block, and the mean block of allgatherv and reduce_scatter,
  each read from counts that are valid on the rank (also with
  `MPI_IN_PLACE`). The v/w collectives whose ranks know only their own
  counts, barrier and the neighborhood collectives have none: loading a file
  in which such a collective can reach a `msg_size` condition fails. A
  trailing `#if ...` makes a *conditional condition*: the
  generated wrapper calls `func` only under that macro guard and returns
  false otherwise.
- **General algorithms** work on any `coll_type`. `MPIR_Coll_nb` runs the
  nonblocking form of a blocking collective and waits for it.
  `MPIR_Coll_buffer_swap` swaps GPU buffers for host buffers (see "GPU
  buffers" below).
- **`<coll>-<intra|inter>` sections** list algorithms. A name such as
  `binomial` expands to the function `MPIR_Bcast_intra_binomial` unless
  `func_name` gives one. Attribute keys:
    - `restrictions`: conditions that must hold for the algorithm to run.
      Threshold conditions and negation are not allowed here; a restriction
      that needs a condition to be false names its own condition. Every
      restriction is then a condition that holds, so the algorithms allowed
      under a set of true conditions are also allowed under any larger set. JSON trees can still negate (`!inplace`).
    - `gpu_swap: 1`: for an algorithm that can't work on device buffers.
      When the `gpu` restriction holds, its generated wrapper swaps the
      buffers for host buffers first (see "GPU buffers" below).
    - `inplace_copy: 1`: for an alltoall, alltoallv or alltoallw algorithm
      that only handles a not-in-place call. When `sendbuf` is
      `MPI_IN_PLACE`, its generated wrapper calls `MPIR_Coll_inplace_copy`,
      which copies the receive buffer span to a temporary buffer and calls
      the wrapper again with that copy as the send side. The algorithm then
      needs no in-place code, and the in-place case costs one copy and
      `p` blocks of extra memory. Such algorithms have no in-place
      restriction, so in-place becomes an ordinary yes/no input of the
      selection. Device buffers are swapped to host first, as with `gpu_swap`.
      Rejected on `general` algorithms and outside the alltoall family.
    - `inner`: for a compositional algorithm, the collectives it calls
      through the selection, as `<section>@<communicator>` (e.g.
      `bcast-intra@node_comm`; communicators `node_comm`, `node_roots_comm`).
      Tuning tools use it to tune the algorithm after those collectives;
      gen_coll only checks the names. A `general` algorithm writes its
      inner calls relative to the caller: `$coll` is the calling
      collective's name, `comm` the caller's communicator, and a suffix
      `[k=v]` sets restriction `k` to 0 or 1 on the inner call. So
      `MPIR_Coll_nb` has `inner: i$coll-intra@comm` and
      `MPIR_Coll_buffer_swap` has `inner: $coll-intra@comm[gpu=0]` (the
      same collective on host buffers). These forms describe the intra case.
    - `extra_params` and `cvar_params`: extra arguments of the algorithm
      function, and the CVAR suffixes that supply them when the algorithm is
      forced by CVAR. The CVAR's type is also the parameter's type in the
      JSON (see below). `name=value` fixes a constant, with `-` as its
      `cvar_params` placeholder.
    - `func_name`, `inline`, `macro_guard`: for device algorithms that are
      inline in device headers and exist only in some builds.
    - `disabled: 1`: keeps the algorithm out of the selection. Forcing it by
      CVAR fails its restriction check, and a JSON file that names it fails
      to load ("disabled algorithm"). Its algorithm table entry is NULL. The
      nonblocking compositions (`sched_smp`) are disabled until nested
      selection into an existing schedule is designed.

Each entry is exactly one algorithm function. There are no aliases; an alias
is a small separate function.

## The decision tree: `coll_selection.json`

Each JSON object is a list of sibling branches, tried in order. A key is a
test and its value is the subtree taken when the test passes. When a test
fails, the next sibling is tried. A leaf is an `algorithm=` key.

| Key form | Meaning |
|---|---|
| `name=bcast-intra-auto` | Top level only: defines a named subtree. |
| `collective=bcast-intra` | Matches the `coll_type` (names from `MPIR_Coll_type_names`). |
| `pof2`, `!pof2` | Boolean condition, optionally negated. |
| `comm_size(8)` | Canonical threshold form: `comm_size <= 8`. |
| `comm_size<8`, `<=`, `>`, `>=` | Aliases: `cond<t` is `cond(t-1)`, `cond>t` is `!cond(t)`, `cond>=t` is `!cond(t-1)`. A leading `!` is an error with these; write `!comm_size(8)` or flip the comparison. |
| `any` | Always true. Every object except an `algorithm=` leaf must have `any` as its last key, so a search never runs past the last case. |
| `algorithm=MPIR_Barrier_intra_k_dissemination` | Leaf. Its object holds the algorithm's extra parameters, e.g. `{"k": 2}`; see below. |
| `"call=bcast-intra-auto"` | A string value in place of an object: continue the search in that named subtree. |
| `"dispatch=bcast-intra(0x820)"` | A string value in place of an object: evaluate the restrictions whose bits are in the mask (here `hierarchical` and `MPIDI_CH4_release_gather`) in one call, `MPIR_Csel_restriction_mask`, and continue in the subtree `bcast-intra-<mask that holds, in hex>`, e.g. `bcast-intra-800`. A combination without a subtree uses that of its largest subset (fewer bits; between equal counts, the lower mask), down to `bcast-intra-0`, which must exist. See "Restriction sets and `dispatch=`" below. |
| `"error"` | A string value in place of an object: end the search without an algorithm, e.g. `"any": "error"` after a list that should cover every case. The collective returns an error. |

The file is a dictionary of named subtrees:

```json
{
    "name=main": "call=auto",
    "name=auto": {
        "collective=bcast-intra": "call=bcast-intra-auto",
        "collective=allreduce-intra": "call=allreduce-intra-auto",
        ...
        "any": "error"
    },
    "name=bcast-intra-auto": {
        "MPIDI_CH4_release_gather": { "algorithm=MPIDI_POSIX_mpi_bcast_release_gather": {} },
        "comm_size<8":              { "algorithm=MPIR_Bcast_intra_binomial": {} },
        "pof2": {
            "msg_size<=12288":  { "algorithm=MPIR_Bcast_intra_binomial": {} },
            "msg_size<=524288": { "algorithm=MPIR_Bcast_intra_scatter_recursive_doubling_allgather": {} },
            "any":                  { "algorithm=MPIR_Bcast_intra_scatter_ring_allgather": {} }
        },
        "any": { ... }
    },
    ...
}
```

- `main` is where every user-level collective starts. `auto` is what nested
  selections search (see below). If a file defines no `auto`, `main` is used.
- The built-in JSON is loaded first. A file named by
  `MPIR_CVAR_COLL_SELECTION_JSON_FILE` is loaded on top of it: each `name=` it
  defines replaces the built-in subtree of that name, and new names are added.
  To retune one collective, a user file only needs that one subtree, e.g.
  `name=bcast-intra-auto`.
- A file with no `name=` keys is loaded as a single tree named `main`.
- `call=` targets are resolved by name at search time, so a subtree replaced
  by the user file is the one used.
- `dispatch=` builds its table of subtrees, one per combination of its bits,
  when the file is loaded, from the subtree names known then; a later file
  that replaces one of those subtrees is used, but a subtree name added only
  by a later file is not.

**Restriction sets and `dispatch=`.** A `dispatch=<prefix>(<bits>)` node
selects among subtrees named by convention `<prefix>-<m>`, where `m` is a
mask of restriction indices (bit k is the restriction with index k in the
`restrictions:` section of `coll_algorithms.txt`) written in lowercase hex
without `0x` or leading zeros: `bcast-intra-0`, `bcast-intra-800`, not
`bcast-intra-0x800` or `bcast-intra-0800`. A subtree spelled otherwise is not
found, and the dispatch falls back as below. `<prefix>` is free-form, e.g.
`bcast-intra`.

At a call, MPICH evaluates the restrictions in `bits`, takes the mask `m` of
those that hold, and continues in `<prefix>-<m>`. If that subtree does not
exist, it continues in the subtree of the largest subset of `m` that does
(fewer bits; between equal counts, the lower mask), down to `<prefix>-0`,
which must exist. Restrictions are positive conditions, so the algorithms a
subset's subtree may select also run under `m`.

The names are only a convention: the loader treats them as ordinary subtrees.
Each subtree must itself select only algorithms whose restrictions hold under
its mask. `<prefix>-800` may select `release_gather` (restriction 11,
`MPIDI_CH4_release_gather`), `<prefix>-0` may not; an algorithm selected where
its restriction does not hold can fail or hang (e.g. `release_gather` before
its shared memory exists).

```json
{
    "name=bcast-intra-auto": "dispatch=bcast-intra(0x820)",
    "name=bcast-intra-0":    { "msg_size(16384)": { "algorithm=MPIR_Bcast_intra_binomial": {} },
                               "any": { "algorithm=MPIR_Bcast_intra_scatter_ring_allgather": {} } },
    "name=bcast-intra-800":  { "msg_size(262144)": { "algorithm=MPIDI_POSIX_mpi_bcast_release_gather": {} },
                               "any": "call=bcast-intra-0" },
    "name=bcast-intra-20":   { "msg_size(65536)": "call=bcast-intra-0",
                               "any": { "algorithm=MPIR_Bcast_intra_smp": {} } }
}
```

Here `0x820` is `hierarchical` (bit 5, `0x20`) and `MPIDI_CH4_release_gather`
(bit 11, `0x800`). The bit numbers in these examples may be out of date: a
restriction's bit is its index in `coll_algorithms.txt`, which changes when
restrictions are removed, so read the current index there. A comm on one node where release_gather can run gets mask
`800`; a comm on several nodes with several ranks per node gets `20`; any
other comm, e.g. one rank per node or release_gather unavailable under
`MPI_THREAD_MULTIPLE`, gets `0`. Both bits holding at once has no subtree, and
would use the lower of `20` and `800`. csel_tuner
(https://github.com/hzhou-muse/csel_tuner) writes files of this shape, with
one subtree per restriction set it measured.

An algorithm leaf lists every non-constant parameter in its `extra_params`
as `"name": value`, and nothing else. The value's type follows the type of the
parameter's CVAR in `cvar_params`:

| CVAR type | JSON value | Example |
|---|---|---|
| `int` | an integer | `"k": 4`, `"chunk_size": 8192` |
| `boolean` | `true` or `false` | `"is_non_blocking": true` |
| `enum` | one of the CVAR's value names, as a string | `"tree_type": "knomial_1"`, `"ccl": "nccl"` |

```json
"algorithm=MPIR_Bcast_intra_tree": { "tree_type": "kary", "k": 4, "is_non_blocking": false }
```

A missing, unknown, or mistyped parameter is an error.

The tree does not check algorithm restrictions. A tree must pick only
algorithms whose restrictions hold on that branch, for example by guarding
`MPIR_Allreduce_intra_reduce_scatter_allgather` with `builtin_op`.

The files are read by a small built-in parser (`csel_json.c`) that accepts
only the JSON subset the tree needs:

- The top level is an object, and every value is an object, a string, an
  integer (fits in an `int`), `true`, or `false`. Floats, arrays, and `null`
  are rejected.
- Strings are printable ASCII without escape sequences. Spaces inside a string
  are dropped, so `"comm_size < 8"` is read as `comm_size<8`.
- Keys within an object must be unique. Objects nest at most 64 levels.
- A syntax error, an unknown subtree, collective, algorithm, or condition, a
  malformed threshold, an object that doesn't end with `any`, or a bad
  algorithm parameter stops `MPI_Init` with the line and column of the error.

## Runtime selection

```
MPI_Bcast
  -> MPIR_Bcast_impl                 (generated) fill coll_sig, MPID_Init_coll_sig,
                                     MPIR_Coll_sig_prepare_gpu
     -> MPIR_Coll_json
        algorithm CVAR set?
          yes: restrictions pass? -> fill container from CVARs ------+
               no: error if MPIR_CVAR_COLLECTIVE_FALLBACK=error,      |
                   otherwise fall through                             |
        MPIR_Coll_run_tree(main)                                      |
          -> MPIR_Csel_search -> container ---------------------------+
                                                                      v
                                          MPIR_Coll_algo_table[id](coll_sig, cnt)
                                            -> <algo>_cnt wrapper -> algorithm
  <- nonblocking: MPII_SCHED_START; persistent: save sched in the request
```

1. **Binding.** `MPI_Bcast` calls `MPIR_Bcast_impl`, as for every other MPI
   function. The `_impl` functions are generated.
2. **Signature.** `_impl` fills a stack `coll_sig`: `coll_type`, `comm_ptr`,
   `flags` (`MPIR_COLL_SIG_FLAG__PERSISTENT` for `_init` calls), `tag`,
   `sched = NULL`, and the arguments. It then calls
   `MPID_Init_coll_sig(&coll_sig)` so the device can add its own fields, and
   `MPIR_Coll_sig_prepare_gpu(&coll_sig)`, which queries the buffers this rank
   uses and sets the GPU flags (see "GPU buffers" below).
3. **CVAR.** `MPIR_Coll_json` reads the algorithm CVAR through
   `MPIR_Coll_cvar_table[coll_type]`, a table of pointers to the CVARs, so a
   value written with `MPI_T_cvar_write` applies from the next call; 0 means
   `auto`. Otherwise it sets `MPIR_COLL_SIG_FLAG__CVAR` and maps the value to
   an algorithm ID (`MPIR_Coll_cvar_to_algo_id`). A value that is not one of
   the collective's algorithms, which only an MPI_T write can set, is an
   error. It then checks `MPIR_Coll_check_algo_restriction`. If the check
   passes, it fills a container from the CVAR parameters
   (`MPIR_Coll_init_algo_container`) and runs the algorithm. If it fails, it
   returns an error when `MPIR_CVAR_COLLECTIVE_FALLBACK=error` and falls
   through to the tree otherwise.
4. **Search.** `MPIR_Csel_search` walks the tree from `main`. A `collective`
   node compares `coll_type`. A condition node calls the generated
   `MPII_Csel_run_condition`, which evaluates the predicate (or `<= thresh`),
   then applies `negate`. `any` always passes. A match moves to `success`, a
   miss to `failure` (the next sibling). A `call` node continues in the named
   subtree. The search ends at a container, or at an `error` node, which
   makes the collective return "Collective selection failed to find an
   algorithm". A search that makes more `call=` jumps than there are
   subtrees is looping, e.g. `auto` → `x` → `auto` for the same collective,
   and returns the same error.
5. **Run.** `MPIR_Coll_algo_table[cnt->id](coll_sig, cnt)` calls the `_cnt`
   wrapper. It increments `MPIR_Coll_algo_counters[id]`, creates the schedule
   for a nonblocking algorithm (`MPII_CSEL_CREATE_SCHED` or
   `MPII_CSEL_CREATE_TSP_SCHED`), and calls the algorithm with the unpacked
   arguments and extra parameters. Back in `_impl`, a nonblocking call starts
   the schedule and a persistent call stores it in a new persistent request.

Rules that follow:

- **Algorithms do not fall back on their own.** An algorithm whose
  restrictions fail is an error. Restrictions are checked once, before a
  CVAR-forced algorithm runs; the tree is responsible for the auto path.
- **Blocking via nonblocking.** `MPIR_Coll_nb` adds 1 to `coll_type`, runs
  selection on the `auto` tree, then starts and waits on the resulting
  schedule. It is chosen by the algorithm CVAR value `nb` or by
  `algorithm=MPIR_Coll_nb` in the JSON.
- **Nested selection.** Because `coll_sig` is passed by pointer and carries
  `sched`, `tag` and `flags`, an algorithm can re-enter selection for a
  sub-step with `MPIR_Coll_run_tree(csel_tree_auto, coll_sig)`. The outer
  entry (`main`) and the inner sub-steps (`auto`) can be tuned separately.
- **One global tree.** There is no per-communicator pruning or caching; every
  call searches from the root.
- **Usage counters.** `MPIR_CVAR_DUMP_COLL_ALGO_COUNTERS=<world rank>` makes
  that rank print a count per algorithm at finalize. Internal `_fallback`
  collectives (used during init and communicator creation) bypass CSEL and are
  not counted.

```
[0] ==== Dump collective algorithm counters ====
[0]          4  MPIR_Bcast_intra_scatter_ring_allgather
[0]         16  MPIDI_POSIX_mpi_bcast_release_gather
[0]          1  MPIR_Reduce_intra_binomial
[0] ==== END collective algorithm counters ====
```

## Generated code

`maint/gen_coll.py` reads the catalog and generates:

| Output | Generated items |
|---|---|
| Types | `MPIR_Csel_coll_type_e`, `MPII_Csel_container_type_e`, `MPIR_Csel_node_type_e`, `MPII_Csel_container_s` |
| Tables | `MPIR_Coll_cvar_table` (constant initializer), `MPII_Coll_type_init` (`MPIR_Coll_type_names`), `MPII_Coll_algo_init` (`MPIR_Coll_algo_table`, `MPIR_Coll_algo_names`), `MPII_Csel_init_condition_names` (`MPIR_Csel_condition_names`, `MPIR_Csel_condition_has_thresh`) |
| JSON parsing | `MPII_Csel_parse_container_params` |
| Search | `MPII_Csel_run_condition` |
| CVAR path | `MPIR_Coll_cvar_to_algo_id`, `MPIR_Coll_init_algo_container`, `MPIR_Coll_check_algo_restriction` |
| Dispatch | the `<algo>_cnt` wrappers and every `MPIR_Xxx_impl` |

`coll_algos.h` is included from `mpir_coll.h`, between `mpidpre.h` and
`mpidpost.h`. Code that calls device functions (conditional-condition
wrappers) goes into `coll_autogen.h`, which is included after `mpidpost.h`.

## Device algorithms

There is no MPID collective ADI. A device takes part in selection by exposing
algorithms that are listed in the catalog, supplying conditions, and adding
fields to `coll_sig`. CH4 POSIX `release_gather` (bcast, reduce, allreduce,
barrier) is the example.

- **Algorithm.** `src/mpid/ch4/shm/posix/posix_coll.h` exposes inline
  functions such as `MPIDI_POSIX_mpi_bcast_release_gather`. The catalog lists
  them with `func_name`, `inline: 1`, and
  `macro_guard: defined(MPIDI_CH4_SHM_POSIX)`; in other builds the generated
  wrapper returns `MPI_ERR_OTHER`. The algorithm CVAR gains the value
  `release_gather`, and the JSON names the function like any MPIR algorithm.
- **Condition.** `MPIDI_CH4_release_gather` is a conditional condition, so the
  same tree works for CH3 and every CH4 configuration.
  `MPIDI_POSIX_check_release_gather` rejects threaded runs, communicators that
  span nodes (`num_external > 1`), and unsupported reduce types or
  non-commutative ops, and it passes only once the shared-memory state is
  ready. It has no side effects: `MPIDI_POSIX_release_gather_prepare`, called
  from `MPID_Init_coll_sig` before the selection, counts the calls on the
  communicator and sets up the shared memory after
  `MPIR_CVAR_POSIX_NUM_COLLS_THRESHOLD` calls, or at once when a CVAR forces
  release_gather. Every communicator, including
  `node_comm` and `node_roots_comm`, carries `MPIR_COMM_ATTR__HIERARCHY`, so
  such checks can rely on the hierarchy fields.
- **Composability.** A condition supplied as a black box, like
  `MPIDI_CH4_release_gather`, must work with tuning tools and with the
  subsets of a tree. It must:
  1. have no side effects: setup such as call counting or shared memory goes
     in `MPID_Init_coll_sig`, before the selection;
  2. depend only on the call's input conditions, the communicator's layout and
     the environment: never on message size or count, and be the same on
     every rank of the call;
  3. be stable after a warm-up of a fixed number of calls on a communicator
     (`MPIR_CVAR_POSIX_NUM_COLLS_THRESHOLD` for release_gather);
  4. be optional: where it is false, the selection without it must be valid;
  5. fail at run time only by turning false (e.g. shared memory exhausted),
     never by returning an error.
- **Signature hook.** Every `_impl` calls `MPID_Init_coll_sig(coll_sig)` after
  the generic fields are set. CH3 defines it as an empty inline; CH4 uses it
  for the release_gather setup.
  New boolean attributes go in the `flags` bit mask.

## GPU buffers

`MPIR_Coll_sig_prepare_gpu` runs before the selection, when GPU support is
on. It queries the buffers this rank uses in the call (e.g. a rooted
collective's recvbuf only at the root, no sendbuf with `MPI_IN_PLACE`) and
sets two flags, which two restrictions read:

| Restriction | Flag | Holds when |
|---|---|---|
| 12 `gpu` | `MPIR_COLL_SIG_FLAG__GPU` | a buffer is device memory (`MPL_gpu_attr_is_dev`) |
| 13 `gpu_coll` | `MPIR_COLL_SIG_FLAG__GPU_COLL` | every buffer is device memory (`MPL_gpu_attr_is_dev`) and `MPIR_CVAR_ENABLE_GPU_COLL` is on |

Buffers that are neither host nor device memory, such as registered host or
managed memory, count as host memory here: the CPU can access them, so the
collective algorithms can use them directly.
`gpu` is a local fact. `gpu_coll` is for algorithms that need device buffers
on every rank; no collective check is affordable in the selection, so the
CVAR is the user's promise that each call passes either host buffers on all
ranks or device buffers on all ranks. Intercomm, alltoallw and neighborhood
collectives are not described yet and never set the flags. Neither flag
changes what any algorithm does: an algorithm without the `gpu` restriction
must still work on device buffers.

`MPIR_Coll_buffer_swap`, a general algorithm with restriction `gpu`, copies
each device buffer into a host buffer (only the ones the
collective reads; a v-collective's recvbuf is copied in too, to keep the gaps
between blocks), points `coll_sig` at the host buffers, clears both flags and
continues in the `auto` tree. Afterwards it copies the written buffers back
and frees the host buffers. With the flags clear, `auto` cannot select it
again; a tree that selects it where `gpu` does not hold gets an error. The
default tree does not use it; a tuning file opts in, e.g. for every
collective:

```
"name=main": {
    "gpu": { "algorithm=MPIR_Coll_buffer_swap": {} },
    "any": "call=auto"
}
```

An algorithm with `gpu_swap: 1` gets the same swap for itself: its
generated `_cnt` wrapper calls `MPIR_Coll_gpu_swap` when the `gpu` flag is
set, which swaps the buffers, clears the flags and calls the wrapper again,
now running the algorithm. Host calls only test the flag. Every other
algorithm must work on device buffers; most do through yaksa, and the
shared CPU step, `MPIR_Reduce_local` with a builtin op that yaksa can't run,
swaps its two operands to host memory itself. Calls that skip the algorithm
table (`MPIR_*_fallback`, one algorithm calling another directly) don't get
the wrapper.

For nonblocking and persistent collectives, `auto` only builds the
schedule, which the generated `_impl` starts afterwards. `buffer_swap` adds
the copies to that schedule before it starts: the copy-ins at the front
(`MPIR_Sched_move_to_front`, or `MPIR_TSP_sched_localcopy_front` for gentran),
then a barrier or fence and the copy-outs at the back. The schedule owns the
host buffers (`MPIR_Sched_add_buffer`, `MPIR_TSP_sched_add_buffer`) and frees
them with itself; a persistent schedule replays the copies on every start. A
call that adds to a schedule an outer collective is already building runs on
the user buffers, since the copies would wrap the outer steps too.

## Adding an algorithm

1. Write the algorithm function with the standard collective arguments, plus
   any extra parameters.
2. List it under its `<coll>-<intra|inter>` section in `coll_algorithms.txt`
   with its `restrictions`, `extra_params`, and `cvar_params`. Add any new
   predicate at the end of `restrictions:` with the next index (a threshold
   condition under `conditions:`) and define its checker function.
3. Add its value to the collective's algorithm CVAR in
   `src/mpi/coll/cvars.txt`.
4. Reference it in `coll_selection.json` on branches where its restrictions
   hold.
